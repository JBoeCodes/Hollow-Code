# Companion protocol (v1)

How the Hollow companion apps (the Mac menu-bar app now; the web app and native iPhone/iPad/Watch apps later) change
vault tasks without writing vault Markdown. Design and reasoning: the vault workspace's
`outputs/companion-apps-2026-10/design.md`. This file is the contract; `docs/companion-op.schema.json` is its JSON
Schema, and `hollow companion-fixtures <dir>` exports golden fixtures generated by the real code.

**Rules.** Vault Markdown stays the truth and Hollow on the Mac stays its only writer. A device never edits a vault
file: it writes a signed, write-once *operation* file. Hollow (`src-tauri/src/companion_inbox.rs`) applies each op
once, through the same task writer agents use (`task_broker`: field validation, compare-and-swap on `contentHash`,
the tracker's lock for tracker-linked tasks), and writes a receipt. Notion two-way sync was removed on 2026-11-10;
a task with only a legacy `notion_id` is a plain vault task.

## Folder: `.hollow-sync/` (vault root, hidden)

```
.hollow-sync/
  pair/<deviceId>.json              # pairing request, written once by a device; Hollow removes it after deciding
  devices/<deviceId>.json           # Hollow's answer: paired / refused / revoked (informational; the trusted key
                                    #   registry lives OUTSIDE the vault, <support>/Companion/devices.json)
  inbox/<deviceId>/<opId>.json      # op envelope, written once by a device; Hollow deletes it after applying
  receipts/<deviceId>/<opId>.json   # written once by Hollow; the device deletes it after reading (Hollow prunes at 30 days)
```

- Write every file to a dot-prefixed temp name in the same folder (`.<name>.tmp`), then rename it into place. Hollow
  ignores dot-prefixed names, so it never reads half a file.
- Never rewrite a file in place (iCloud makes conflict copies of rewritten files). Names are unique per op.
- The dot prefix keeps the folder out of the vault watcher, search and History. Agents are refused writes there by
  Hollow's own write gates (`run_guard::is_protected_path`); the real boundary is the signature: an agent can drop
  a file, but it can't sign as a paired device.

## Identifiers and encodings

| Thing | Format |
|---|---|
| `deviceId` | `^[a-z0-9][a-z0-9-]{2,63}$`, chosen by the device, e.g. `mac-7f3a2b1c` |
| `opId` | ULID, `^[0-9A-HJKMNP-TV-Z]{26}$` (Crockford base32, upper case) |
| `ref` | `vault:tasks/<file>.md` (what Hollow's task tools return) |
| `contentHash` | lowercase hex SHA-256 of the task file's exact bytes |
| `publicKey` | base64 (standard, padded) of the 65-byte uncompressed P-256 point `04‖x‖y` (CryptoKit `x963Representation`, WebCrypto `exportKey("raw")`) |
| `sig` | base64 of the 64-byte ECDSA P-256 / SHA-256 signature `r‖s` (CryptoKit `rawRepresentation`, WebCrypto's output) |
| times | RFC 3339 UTC, e.g. `2026-10-12T20:41:07.123Z` |
| dates | `YYYY-MM-DD`; clock times `HH:MM` (24 h) |

## Pairing

1. In Hollow: Settings → Devices → Companion devices → **Pair a device**. Hollow shows an 8-character code (`XXXX-XXXX`,
   Crockford base32) for 10 minutes. The code exists only in Hollow's memory; it is never written to disk. Five wrong
   proofs close it.
2. The device generates its P-256 key (Secure Enclave where available), and writes `.hollow-sync/pair/<deviceId>.json`:

```json
{ "v": 1, "deviceId": "mac-7f3a2b1c", "name": "Alex's MacBook (menu bar)", "platform": "macos",
  "publicKey": "BC3q…", "at": "2026-10-12T21:00:00Z", "proof": "base64…" }
```

   `platform` is one of `macos`, `ios`, `ipados`, `watchos`, `web`. `name` is at most 80 characters.
   `proof = base64(HMAC-SHA256(key = code, message = "hollow-pair-v1\n" + deviceId + "\n" + publicKey))`, where
   `code` is the 8 code characters upper-cased with the dash and spaces removed, as UTF-8.
3. Hollow checks the proof against the open code, stores the key in `<support>/Companion/devices.json`, closes the
   code, deletes the request and writes `.hollow-sync/devices/<deviceId>.json`:
   `{ "v": 1, "deviceId", "name", "platform", "status": "paired" | "refused" | "revoked", "reason"?, "at" }`.
   A request with no open code, a wrong proof, a malformed key or a `deviceId` already paired with a different key is
   refused (the file says why). Re-pairing the same `deviceId` with the same key is accepted.
4. Revoking (Settings → Devices → Companion devices → Revoke) deletes the key; later ops from that device are refused.

## Op envelope

`inbox/<deviceId>/<opId>.json`:

```json
{ "v": 1, "deviceId": "mac-7f3a2b1c", "opId": "01JA9M3Q…", "payload": "{\"v\":1,…}", "sig": "base64…" }
```

`sig` signs the **exact UTF-8 bytes of the `payload` string**. Hollow verifies those bytes and only then parses
them. (Signing a string avoids canonical-JSON rules that Swift, TypeScript and Rust would have to agree on byte for
byte.) The payload's `v`, `deviceId` and `opId` must equal the envelope's, and the file name must be
`<opId>.json` in the `<deviceId>` folder. Envelopes over 64 KiB are refused.

Payload, common keys: `v` (1), `opId`, `deviceId`, `at`, `kind`. Unknown keys are refused.

### Kinds (v1: tasks)

| `kind` | Keys | Hollow applies it as |
|---|---|---|
| `task.create` | `title` (required), `status`, `priority` (`P1` to `P4`), `due`, `dueTime`, `durationMin` (1 to 1440), `recurrence`, `labels` (array), `description`, `projectUrl` (a project's `vault:` ref) | `create_task` with idempotency key `companion:<opId>`; `origin: companion:<deviceId>`. Local only: never created in the tracker |
| `task.update` | `ref`, `baseHash`, `fields`: `{ <field>: { "from": v, "to": v } }` for `title`, `priority`, `due`, `dueTime`, `labels`, `description` | `update_task`, per-field merge below. `null` or `""` means empty/absent; `labels` is an array of strings |
| `task.set_status` | `ref`, `baseHash`, `from`, `to` | `set_status` (a recurring task rolls its due date forward instead of finishing) |
| `task.comment` | `ref`, `text` (≤ 2,000 chars) | `add_comment` with an activity marker from the opId, so a repeat never doubles it |

Validation is the task broker's (titles ≤ 240 chars, one line; priority P1–P4; statuses one line ≤ 60 chars; ≤ 20
labels). On a tracker-linked task a field its issue holds is refused (the broker's `TASK_LINKED`).

### Kinds (overnight 10-12/13: notes and workspace lines)

Applied by `src-tauri/src/companion_notes.rs` with the same ledger, lease and receipts. A Hollow that applies them
declares them in `X-Hollow-Kinds` (below); the installed `e410ec8f` doesn't, so the backend keeps such ops queued for
it rather than let it refuse them.

| `kind` | Keys | Hollow applies it as |
|---|---|---|
| `note.create` | `title` (1–200 chars, one line), `body` (≤ 48 KiB of UTF-8; the whole op must fit 64 KiB), `folder` (`notes`, the default, or `library/notes`) | a new file `<folder>/<title as a file name, ≤ 100 bytes>.md` with front matter `title`, `created`, `source: companion: <device name>`, `companion-op: <opId>`. Never overwrites: a taken name (in any letter case) gets ` 2`, ` 3`… |
| `note.edit` | `ref` (`vault:notes/…` or `vault:library/notes/…`), `baseHash` (the file's SHA-256 the device read), `body` (≤ 48 KiB: exactly what `/api/v2/docs/<path>` returns as `body`, the text after the front matter's closing `---` line with its blank line; sent back unchanged it round-trips byte for byte) | replaces the body and keeps the BOM and front matter. When the file changed since (`baseHash` differs), nothing is overwritten: the device's version is saved beside it as `<name> (from <device> <date>).md` (its `title` gets `(from <device> <date time>)` too, so the two notes don't share a title; a note without a title, or with a block-scalar one, keeps its front matter as it is), the receipt is `conflict` with `ref` = that copy and a `reason` naming both |
| `note.append` | `ref`, `text` (1–10,000 chars) | a new paragraph at the end, then a hidden `<!-- op:<opId> -->` comment on its own line (visible in source view) |
| `workspace.append` | `workspace` (id), `file` (`plan` or `brief`), `text` (one line, ≤ 2,000 chars) | `plan`: `- [ ] <text> (<device>, <date>)` under `## From your devices` at the end of PLAN.md; `brief`: `- <date time> · <device>: <text>` at the end of WORKSPACE.md's `## Current context` (each section added when missing) |

A device may make at most 200 new files in any 24 hours (tasks and notes created plus conflict copies saved); more is
`refused` until the window rolls on. A repeat of an op that already made its file is still answered. A client whose
op was refused this way should keep the text and send it again later under a new `opId`.

Applying twice is harmless: if Hollow stops after applying and before its ledger write, the op comes again, and each
kind sees it already happened (the created note's `companion-op`, the appended `<!-- op:… -->` comment, an edit whose
result is already on disk, a conflict copy found by its marker). Only a held vault lease or a passing I/O problem makes
an op wait; anything that can't clear by itself (not UTF-8, a folder, a locked file, a bad path) is `refused`, so one
op never stalls a device's queue. A `conflict` receipt here has an empty `conflicts` list (it is about the whole note).

Every target must be a path the backend mirror may hold in the person's scope (`companion_docs::classify` and
`<support>/Companion/scope.json`: a note under `notes/` or `library/notes/`, a workspace on the personal list, work data
only with work data on) with no symlink anywhere on it and no letter-case mismatch. Anything else is `refused`. Project
edits aren't offered yet (tracker-synced work data).

### Applying when the file moved (per-field merge)

If the task's current `contentHash` equals `baseHash`, every field applies. Otherwise Hollow re-reads the task and,
per field (status counts as one field), merges three ways:
- current == `from`: apply `to`;
- current == `to`: already so, nothing to do;
- otherwise: a **conflict**. The other fields still apply; the conflict goes to *Waiting on you* as a
  `companion_conflict` card (**Use the device's value** / **Keep the Mac's**), and the receipt lists it.

Values compare after normalising: trimmed strings, `null` = `""`, priority as `P1`–`P4`, labels as a list, status
case-insensitively.

**Repeating tasks.** Finishing a task with a `recurrence` rolls its due date forward and resets its status, so the
status reads `from` again afterwards. A `task.set_status` to a finished status on a repeating task therefore applies only
when `baseHash` still matches; otherwise the receipt is `conflict` with a `reason` and no card (using the device's value
would roll it forward a second time).

### Old ops ask first

An op whose signed `at` is more than 14 days before Hollow sees it (a device that was offline for weeks, or a backlog
on the backend) is not applied on arrival, on either road. Hollow verifies it, keeps its exact envelope in the ledger's
database (`held` table, outside the vault), and raises a `companion_old_op` card in *Waiting on you* ("Old change from
a device": what it does, which device, when it was sent): **Apply it** verifies the kept envelope again against the
device's key and applies it through the same path and ledger as a fresh op (so a moved file still merges per field
and a true overlap still makes a `companion_conflict` card); **Discard it** answers `refused` with a reason and applies
nothing. Until then the device gets **no receipt** (it keeps showing the op as waiting); a copy that arrives again is
held again with no second card, and is never opened (the kept original is what Apply it verifies, so a damaged or
forged copy can't get the op answered `refused`). After the decision a later copy gets the stored receipt. The answer
goes back by each road the op came by: a receipt file for an inbox copy; for a backend copy the decision also writes
an `outbox` row in `applied.db`, and the bridge posts that receipt (`POST /api/v1/applier/receipts`) before its next
poll, keeping the row until the daemon answers 200 (removing the backend in Settings drops the rows still owed to it
and forgets which held ops it handed over). A poll can't do it: the daemon expires an unapplied newer-kind op
(`note.*`, `workspace.append`) 14 days after receiving it and never hands it out again, and the real receipt replaces
its `expired` one. Apply it checks the card first: its fingerprint, `opKind` and `sentAt` must still match the held op
(card text is in the vault, where an agent can edit it), else "This card changed; discard it." Discard it needs no
match: it answers the held op the card was raised for, read from its fingerprint (an edit to the card's details doesn't
change it; a raw edit of the queue file could, and the run guard flags that). An op the task broker
refuses when applied gets its `refused` receipt and the card closes with the reason (a retry can't help); a busy
vault puts the card back to pending. Revoking the device drops its held ops and closes their cards. An `at` in the
future is not old.

## Receipt

`receipts/<deviceId>/<opId>.json`, written once:

```json
{ "v": 1, "opId": "01JA…", "deviceId": "mac-7f3a2b1c", "at": "…", "status": "applied",
  "ref": "vault:tasks/call-jordan.md", "contentHash": "…", "applied": ["due"], "conflicts": [],
  "task": { "title": "…", "status": "Not started", "due": "2026-10-15" }, "reason": null }
```

| `status` | Meaning |
|---|---|
| `applied` | every field applied or was already so (`applied` lists the ones that changed something) |
| `partial` | some fields applied; `conflicts` lists the rest as `{ field, base, device, mac }` |
| `conflict` | nothing applied, and at least one field conflicts (the rest were already so) |
| `refused` | nothing written: unsigned or unknown device, bad signature, invalid field, unknown ref, a field a tracker issue holds. `reason` says why |
| `expired` | issued by the backend, not Hollow: an op of a newer kind (`note.*`, `workspace.append`) that no Hollow applied within 14 days (never one handed out in the last 6 hours). A real receipt that arrives later replaces it |

`task` is the task as saved (so a device shows a recurring task's next due date, not "done"). A duplicate delivery of
an op already applied gets the stored receipt again; nothing is applied twice (a held old op gets no receipt until
its card is decided, above). The applied-op ledger is
`<support>/Companion/applied.db`, outside the vault, keyed by `(deviceId, opId)`, and it records only ops whose signature
verified: a refusal before verification (unpaired device, bad signature, malformed file) gets a receipt but no ledger row,
so a damaged or forged file can't claim an opId and the device's genuine resend still applies. Hollow records an op in
the ledger before writing its receipt.

Hollow never follows a symlink inside `.hollow-sync/` (folders or files): a linked folder is skipped and nothing is
written through it.

## When Hollow applies

Hollow watches `.hollow-sync/inbox/` and `.hollow-sync/pair/` and also scans every 60 s. Ops are applied under a short
background write lease: while an automated run holds the whole vault, ops wait in the inbox and are applied after it.
Ops from a Mac app land within seconds while Hollow runs; while Hollow is quit they wait and apply at the next launch.

## Fixtures

`hollow companion-fixtures <dir>` writes `fixtures.json` (and copies of the task files it used): task files with
Hollow's parse, quick-add inputs with `quick_add::parse` outputs, pairing-proof and signature vectors, and op cases
(task before, op, receipt, task after) produced by running the real applier in a temporary vault. The companion repo
pins a copy and tests its Swift and TypeScript code against it.

## The backend road (W1)

A device that can't reach the vault folder (the web app; phones later) sends the **same envelope** over HTTP to
`hollow-companiond` (the companion repo's `server/`, contract `docs/BACKEND_API.md` there) and reads receipts and a
read-only task mirror from it. Hollow (`src-tauri/src/companion_bridge.rs`) long-polls the daemon and runs each
envelope's exact text through the same verification, task broker and applied-op ledger as the inbox, so an op that
arrives on both roads applies once (the second copy gets the stored receipt). Backend pairing uses the same request
body and the same in-memory code; Hollow decides and pushes the paired-device list. On this road a device Hollow already
knows still needs a fresh code to pair again (the request is unauthenticated there); a device paired over the inbox
road (the menu-bar app) also needs a fresh code to get a backend token. A request whose answer was lost gets the same
decision when it comes back (Hollow remembers decisions by the daemon's ticket for 15 minutes). The mirror holds only task files
under `tasks/` and project `ref`/title/status. A mirrored task row is `companion_inbox::task_json`; a tracker mirror's
row also carries `statusType`, `trackerKey` and `trackerUrl` (each only when known) from `task.tracker`, the same fields
and spellings as the phone API's `/v1/tasks` rows (`docs/phone-api/tracker.md`), and a local task's row omits them. Receipts on this road go back to the daemon, not into `.hollow-sync/`.

**Bridge generations and kinds.** A Hollow with the v2 bridge sends `X-Hollow-Bridge: 2` (it pushes documents) and
`X-Hollow-Kinds: <comma list>` (exactly the op kinds its applier applies, `companion_inbox::APPLIED_KINDS`) on every
applier call. The installed `e410ec8f` sends neither. The daemon hands an applier only the kinds it declared, and
without the header only `task.create`, `task.update`, `task.set_status`, `task.comment`, because an applier refuses
an unknown kind (or an unknown key) with a refused receipt that burns the op id. The v2 bridge also
pushes the document mirror (`companion_docs.rs`; the companion repo's `docs/BACKEND_V2.md`).
